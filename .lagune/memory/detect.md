# yaml.min Detect Map

- **Scope:** The `./src` directory: the public parse entry point, its shared parser state type, and the internal block, flow, string, scalar, navigation, and character modules.
- **Mapped:** 2026-11-12

## Findings

### The nesting depth limit does not cover every recursion path

- **What it is:** The parser sets itself a maximum nesting depth of one thousand levels and raises a clear error past it. That counter is incremented in exactly one function, the indentation-style value parser. Two other recursion paths never touch it: the branch that handles collections written compactly on a single line (`- - - - x`), which calls itself once per level, and the bracket-and-brace readers, which recurse into one another through the flow value reader with nothing counting the levels. Nesting that arrives on separate lines is counted and rejected correctly. Nesting that arrives on one line, or inside brackets, is not counted at all.
- **Why it matters:** Half the parser sits outside the guard the project already wrote, so a document can nest without limit and runs out of native stack instead of hitting the ceiling. Measured on **Node.js** 26 with its default stack: about 3,900 levels written compactly, under 8 KB of input, crash with `Maximum call stack size exceeded`, and 2,000 levels build successfully although the stated limit is 1,000. About 3,300 nested brackets, roughly 6.6 KB, crash the same way on the flow path. A stack overflow is not a parse error a caller can recover from cleanly, and it surfaces as a low-level engine fault rather than the parser's own intentional error, so an application that distinguishes a bad document from an internal fault gets the wrong answer and typically reports a server fault instead of a rejected input. This library is a dependency inside other people's servers, build pipelines, and CI, so a few kilobytes of hostile YAML take down whatever embedded it. The single test that pins the limit builds roughly a thousand nested block sequence items and expects the error, so it passes on the one path that is guarded and leaves both unguarded paths unpinned, which is exactly how the gap stays invisible.
- **Evidence:** The depth counter is declared on the shared parser state record and initialized by the public entry point, and only the indentation-style value parser increments it and raises the error. The compact-sequence branch of the inline value parser recurses into itself for each dash on the same line without re-entering it, and the flow sequence, flow mapping, and flow value readers recurse into one another with no reference to it anywhere. The limit and its single check arrived together in the project's first commit, and nothing in the history or the code records a reason to leave the other paths out. The error the limit raises is a `RangeError`, the same class the engine throws on a stack overflow, so even the guarded path cannot be told apart from an engine fault by its type. The maximum-nesting-depth test in the edge-case suite exercises only the counted path and expects that `RangeError`.

### Alias expansion has no fan-out, depth, or size budget

- **What it is:** An anchor stores a value under a name and an alias hands the stored value straight back, by reference rather than by copy. The resolver keeps no count of how many times an anchor is referenced, how deeply aliases chain into each other, or how large the referenced value is, and anchors accumulate for the whole document with no cap. Both the indentation-style and the bracket-and-brace readers store whatever the lookup returns without any budget on the path.
- **Why it matters:** Because the value is shared rather than copied, parsing stays fast and memory stays proportional to the input, so the "aliases never copy" expectation holds during the parse. The blow-up simply moves to the first consumer that walks the result. Measured directly: 288 bytes of chained aliases, eight layers of nine references each, parse instantly and serialize to about 206 MB, an amplification of more than 700,000 times, and each further layer multiplies the result by nine again. The application never sees a large document, only a small one, so any size check it performs passes, and the exhaustion lands later, when it serializes, deep-clones, schema-validates, merges, or re-emits the result. This is the classic entity-expansion denial of service, deferred one step past the parser. Separately, because branches are shared, an application that edits one entry silently edits every other entry that referred to the same anchor, which is not how a parsed tree is normally assumed to behave. Nothing pins the sharing either: several tests use anchors and aliases but every one compares with deep equality, which passes identically whether the alias returned the same reference or a fresh deep copy, so a future change that deep-copies alias values, the obvious reach when fixing the mutation surprise, would pass the whole suite while turning the deferred amplification into an immediate one.
- **Evidence:** The alias resolver, which looks the name up in the anchor store and returns the stored value directly, together with the anchor store it reads and the anchor-recording helper that writes into it. The flow sequence reader pushes the lookup result straight into its result array and the flow mapping reader stores it as a value the same way. None of them carries an expansion count, a chain-depth limit, or a total-size budget. The anchor and alias test blocks in the feature and edge-case suites all assert with deep equality and none asserts identity.

### Mapping keys are coerced to strings, so distinct keys silently collide

- **What it is:** Every key parsed from a mapping is resolved to a typed value and then converted to a string before it is stored, and nothing checks whether that string was already used by an earlier entry, so a later entry silently replaces an earlier one.
- **Why it matters:** YAML v1.2 treats a duplicate key as an error. Here the collision is invisible, and the coercion manufactures collisions between keys the author wrote as different. Confirmed by running the parser: `0x10` and `16` both become the key `16`, `1.0` and the quoted `"1"` both become `1`, the keys `null`, `~` and the empty string all collapse to a single empty-string key, a plain repeated key keeps only the last value, and in the bracket-and-brace path every mapping-shaped key collapses to the identical name `[object Object]`, so a document with two different complex keys returns a single entry with the first one gone and no error. In a policy or configuration file the value that actually takes effect is not the one a reviewer reads, and a document can carry a benign-looking entry silently overridden by a later one that a spec-conformant parser would have rejected outright. Nothing in the suite or the snapshot corpus feeds a document that names the same mapping key twice in either syntax, so the behaviour is unrecorded, unasserted, and free to change without any test noticing.
- **Evidence:** The key stringification step applied immediately before the guarded assignment on both the ordinary mapping entry path and the explicit-key path, and the plain string conversion the flow mapping reader applies to its key, neither of which checks whether the resulting name is already present on the target object. The snapshot corpus and the end-to-end suites contain no mapping with a repeated key.

### Block and flow mappings stringify the same key by different rules

- **What it is:** Both mapping styles must turn a parsed key into a property name and they do it two different ways. The indentation style uses the shared key-stringifier. The bracket-and-brace style uses a plain string conversion instead. The same key therefore lands under different names depending only on which syntax the document used: a list key becomes `a,b` in one style and `["a","b"]` in the other, and an empty key becomes `null` in one and an empty name in the other.
- **Why it matters:** The same logical document written in the two syntaxes produces objects with different key names, so a tool that inspects one form and a system that consumes the other disagree about what the document says. That is exactly the parser-differential condition a policy bypass is built on, and it needs no second parser to exploit: one library reading one file two ways is enough. Verified by running both forms side by side.
- **Evidence:** The flow mapping reader converts its parsed key with a plain string conversion before handing it to the shared key-assignment helper, while the indentation-style reader passes the same kind of key through the shared key-stringifier first.

### Numeric scalars are coerced with no precision or range check

- **What it is:** Any text shaped like a number is handed to the platform's integer and floating-point converters and the result is returned as-is, with no check that the value survived the conversion intact. A twenty-digit integer comes back rounded to a different number. A large hexadecimal value comes back as an approximation. A leading zero is dropped. An out-of-range exponent becomes infinity, and the document can also name infinity and not-a-number directly.
- **Why it matters:** Values that look like numbers but are really identifiers, account references, postal codes, or precise amounts come back altered, and an application comparing what it read against what it stored finds they no longer match. Worse, infinity and not-a-number are outside what JSON can represent, so they vanish into nulls the moment the result is serialized, meaning a field that held a document-supplied value at one point in the application holds nothing at another. A numeric comparison that guards a limit can be steered by choosing a value that changes when it is converted.
- **Evidence:** The scalar resolver dispatches number-shaped text to the integer resolver, then to the floating-point conversion, then to the infinity and not-a-number cases, and returns each result directly with no bound or fidelity check applied to any of them. Confirmed by running the parser: `12345678901234567890` returns `12345678901234567000`, `01234` returns `1234`, and `1e999`, `.inf`, and `.nan` all serialize to `null`.

### Explicit type tags are discarded, so values keep the type the parser guesses

- **What it is:** A YAML document can state a value's type outright with a tag such as `!!str`, `!!bool`, `!!int`, or `!!null`. The parser reads past every tag and throws it away without telling anyone, then decides the type from the bare text alone, exactly as if the tag had never been written. Tags it does not recognise, including application-specific ones like `!custom`, are dropped the same way instead of being refused.
- **Why it matters:** The document says one thing and the program receives another, and the difference can turn a setting from off to on. Confirmed by running the parser: `enabled: !!bool "false"` returns the text `"false"`, which JavaScript treats as true, so a switch the author explicitly declared off reads as on in any ordinary `if` check, failing open. `zip: !!str 0123` returns the number `123` with its leading zero gone, `version: !!str 1.10` returns the number `1.1`, `limit: !!int "5"` returns text instead of a number, and `token: !!null "secret"` hands back `"secret"` where the author declared no value. A reviewer, a schema validator, or any spec-conformant parser honours these tags, so they all read a different value from the same bytes than **yaml.min** does, which is the parser-differential condition a policy bypass is built on. A document written for a schema this library does not support parses quietly instead of failing, so nothing tells the caller that part of the document's meaning was ignored.
- **Evidence:** The anchor-and-tag reader, which steps over any token starting with an exclamation mark up to the next whitespace and records only anchors, so no caller ever learns a tag was present. It has done so since the project's first commit, and nothing records an intended tag set. The scalar resolver then guesses the type from the plain text, and quoted text always stays a string. The same reader serves the indentation-style value parser, the block sequence and mapping readers, and the flow sequence and mapping readers, so the tag is lost in both syntaxes: `[!!str 10, !!bool "false"]` returns `[10, "false"]`.

## Applied specializations

- regex: applied as the required entry, with its checker run across the whole project. It reported no unsafe pattern, and the three patterns in the parser source (the document character-screening pattern and the float and infinity patterns) each checked `safe` individually, so it surfaced no finding.
- javascript: applied across the parser source. Its coercion terrain surfaced "Mapping keys are coerced to strings, so distinct keys silently collide", "Block and flow mappings stringify the same key by different rules", and "Numeric scalars are coerced with no precision or range check". Its terrain on synchronous work blocking a single-threaded event loop and on unbounded resource use surfaced "The nesting depth limit does not cover every recursion path" and "Alias expansion has no fan-out, depth, or size budget". It also confirmed the parser source contains no `eval`, `Function` constructor, `vm`, subprocess, filesystem, or dynamic `require` path, and routes every mapping-key assignment through the single guarded helper.
- interpreter: applied to the parser source as a deserializer. Its pre-pass checker found no dynamic-execution sink, and reading the tag handling confirmed no tag, type, or directive is ever resolved into a constructed instance or a function. The same reading surfaced "Explicit type tags are discarded, so values keep the type the parser guesses", since every tag, including the inert core-schema type tags, is dropped rather than honoured or refused.
- xml: applied for its entity-expansion terrain, which anchors and aliases implement directly. Its billion-laughs guidance (cap the expansion count, the nesting depth, and the total expanded size) is the control missing from "Alias expansion has no fan-out, depth, or size budget". Its external-entity terrain is absent: the parser resolves nothing outside the document and performs no I/O.
